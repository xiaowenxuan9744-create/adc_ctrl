# Testplan Generator - 验证计划生成器

根据设计规格 + RTL 代码自动生成验证计划，定义测试点、覆盖率目标和验证策略。

**设计原则：简洁优先。** 测试点应聚焦核心功能和典型边界场景，禁止为覆盖率数字而堆砌无意义的测试点。每个测试点必须有明确的验证目的。

**文件组织：每个 test case 独立文件管理。** 验证计划中定义的每个 test case 应对应一个独立的 testbench 文件（`tb_<module>_<case_name>.sv`），禁止所有 case 塞进同一个文件中。

**关键约束：必须一次生成完整初版。** 严禁线性从左到右罗列功能点后靠人工多轮 review 补漏。通过多视角并行分析 + 完整性自检，一次性输出全覆盖的测试计划。

## 输入

- **设计规格文档**（Markdown / Word）— 必需
- **RTL 代码文件**（.v / .sv）— 必需
- spec_parser 输出的 JSON（可选）
- 功能点列表（可选）

## 输出

- 验证计划文档（Markdown）
- 测试点清单（按优先级分级，标注 spec 引用 + RTL 位置）
- 覆盖率目标矩阵

## 流程

### Step 1: 多视角并行分析

同时启动三个独立分析代理（使用 Workflow 并行调度）：

子 agent **只读不写**——通过 schema 返回结构化数据，由主 session 统一调用 Write 写文件。

```
workflow script:
  phase("功能覆盖")
  phase("RTL 分析")
  phase("边界挑战")

  // 子 agent 只读——通过 schema 返回结构化数据
  const [specFPs, rtlPaths, edgeCases] = await parallel([
    () => agent("从 spec 提取所有功能点",
               {phase: "功能覆盖", schema: FP_SCHEMA}),
    () => agent("从 RTL 代码提取所有逻辑路径、FSM、CDC",
               {phase: "RTL 分析", schema: RTL_SCHEMA}),
    () => agent("挑战测试计划找漏洞：异常、竞争、跨域",
               {phase: "边界挑战", schema: EDGE_SCHEMA}),
  ])

  // 合并去重、完整性自检（在主 session 中完成）
  phase("输出")
  const merged = merge(specFPs, rtlPaths, edgeCases)
  const report = generateReport(merged)
  // 主 session 统一写文件——权限弹窗在主对话可见
  Write("spec/testplan_" + projectName + ".md", report)
```

#### Agent 1：功能覆盖分析

输入：spec 文档
输出：功能点清单（按功能域分类，标注 spec 章节引用）

覆盖范围：
- 所有配置寄存器（每个位域：名称、属性、复位值、位宽）
- 所有接口信号（每个方向、位宽、时序描述）
- 所有功能模式描述（正常模式、特殊模式、配置流程）
- 所有时序图/状态图描述
- 所有参数和可配项

#### Agent 2：RTL 实现分析

输入：所有 RTL 代码文件
输出：RTL 实现的逻辑路径清单（标注文件+行号）

覆盖范围：
- 所有 FSM 状态和转移路径（列出所有状态和转移条件）
- 所有组合/时序逻辑块
- 所有 generate 分支（每个参数组合）
- 所有跨时钟域同步器（标注源域→目标域、同步器类型）
- 所有参数和配置路径
- 所有计数器边界（最大值、溢出条件）
- 所有寄存器的读写路径（位域映射）
- 所有状态机 default 分支和非法状态处理

#### Agent 3：边界挑战分析

输入：spec + RTL 代码
输出：隐藏挑战点清单

覆盖范围：
- 异常场景（非法输入、时序竞争、同时触发）
- 跨域交互（CDC 多周期、频率关系反转、读后写竞争）
- 复位行为（采集中复位、复位后重使能、复位时序）
- 信号粘着（电平信号长时间保持、脉冲非预期展宽）
- 边界值（计数器满、序列边界、通道边界、SPT 边界）
- 设计未定义行为（FSM 非法状态编码、空序列、未初始化寄存器）
- spec 与 RTL 的不一致之处（属性、位宽、复位值）
- 外部接口异常（ack 无 req、使能关闭时有事件）

### Step 2: 合并去重与完整性检查

三个 agent 独立输出后，合并为统一的测试点清单：

1. **去重**：对跨 agent 的重复测试点只保留一份，以 spec 引用为准
2. **交叉标注**：每个测试点标注 spec 章节 + RTL 文件行号，确保可追溯
3. **优先级分级**：
   - P0：核心功能——寄存器读写、主数据通路、中断、复位、跨时钟域
   - P1：边界条件——位域、边值、同时事件、源选择、使能门控
   - P2：异常/深层场景——非法状态、频率反转、连续模式、不可测场景标记
4. **完整性自检**：合并后立即执行以下检查，未通过则重新生成：
   - ✅ 每个 spec 功能域是否有 ≥1 个测试点对应？
   - ✅ 每个 RTL 模块是否有测试场景覆盖？
   - ✅ 是否遗漏了跨域/异常/竞争类场景？
   - ✅ 是否有不可测的测试点已标注说明？
   - ✅ spec 与 RTL 的不一致处是否已生成测试点（标记为需决策）？
   - ✅ 是否有在 RTL 中实现但 spec 未定义的逻辑路径被遗漏？

**完整性自检是流程的最后一步，不是 review 的第一步。不依赖人工多轮 review 来发现遗漏。**

### Step 2a: 不可测点处理

合并去重后，对标记为"不可测"的测试点按以下规则处理：

| 类型 | 处理方式 | 示例 |
|:--|:--|:--|
| **确实不可测**（芯片级时序、物理特性） | 标注原因，归档到"验证范围外"章节 | 模拟接口在特定时钟沿产生的精确时序 |
| **成本过高但可测**（如形式化验证） | 标注建议的替代验证方法 | FSM 非法状态恢复 → formal property checking |
| **行为未定义**（spec 未定义的行为） | 标注"需设计决策"，不删除 | 同时 SW + MCTM 触发到达的设计优先级 |
| **RTL 与 spec 不一致** | 标记为"需决策"，纳入测试计划 | WO 位读回非零 |

### Step 2b: 边界挑战三分类

边界挑战 Agent 输出的"问题点"不得直接作为 testplan 的测试点或直接判定为 RTL bug。
必须经过三分类判定后分别处理：

```
边界挑战 Agent 输出问题清单
        ↓
  自动三分类判定
        ↓
┌──────────────────────────────────────────────┐
│ 1. RTL bug                                   │
│    判定条件：spec 有明确定义，RTL 行为不符    │
│    处理：标记为 RTL_BUG，同步给设计修复，     │
│          修复重新生成 testplan               │
│    例：CONT_MODE spec 有、RTL 硬编码 1'b0    │
├──────────────────────────────────────────────┤
│ 2. 验证预期错误                              │
│    判定条件：RTL 行为符合设计意图，           │
│              testplan 预期写错了              │
│    处理：修正 testplan 的预期结果，           │
│          不修 RTL                            │
│    例：DMA_ACK 优先于新事件——设计就是如此    │
├──────────────────────────────────────────────┤
│ 3. 需决策                                    │
│    判定条件：spec 未定义，或可靠性/成本权衡   │
│    处理：附上分析（影响+原因）请你决策，      │
│          决策后决定修 RTL 还是改 testplan     │
│    例：cal_done 粘着是否加超时？             │
└──────────────────────────────────────────────┘
        ↓
第 1 类 → 提交修复 RTL → 按影响范围标记更新 testplan
第 2 类 → 修正 testplan 预期 → 继续
第 3 类 → 附分析请你决策 → 决策后走第 1 或第 2 类路径
```

### 三分类判定树

三分类不得依赖模型自由发挥，必须按以下判定树逐级执行：

```
对每个边界挑战点：

Step A: spec 是否定义了该行为？
  ├─ 有明确定义 → 进入 Step B
  ├─ spec 描述模糊/不完整 → 第 3 类（需决策），标注"spec 不明确"
  └─ spec 完全没有提及 → 第 3 类（需决策），标注"spec 未定义"

Step B: RTL 行为与 spec 定义是否一致？
  ├─ 完全一致 → 第 2 类（验证预期错误）
  │   └─ 判定：testplan 的预期写错了，不是 RTL bug
  │   └─ 处理：修正 testplan 预期以匹配 RTL+spec
  └─ 不一致 → 进入 Step C

Step C: RTL 行为是否符合设计意图？
  ├─ 是——RTL 行为合理，但 spec 描述不准确 → 第 3 类（需决策）
  │   └─ 建议：更新 spec 以匹配实际 RTL 行为
  │   └─ 例：WO 位读回非零——硬件设计合理但 spec 没对齐
  └─ 否——RTL 行为是错误的 → 第 1 类（RTL bug）
      └─ 例：CONT_MODE spec 要求连续模式，RTL 硬编码单次
```

按此树判定后，每个边界挑战点的分类理由必须是可追溯的（标注 Step A/B/C 的判定路径）。

**影响范围标记**：每个 RTL bug 必须标注它影响的测试点 ID 列表，修复后只重置这些测试点的状态为"待验证"，不触及无关测试点。

RTL bug 记录格式（示例）：
```
问题: MISS_001 — <信号> 请求未对齐导致 FSM 死锁
文件: <module>_fsm.v:<行号>
影响测试点: <TP_ID_1>, <TP_ID_2>, <TP_ID_3>
修复后状态重置: 待验证（仅上述 3 个点，其余不受影响）
```

**禁止**：未经三分类直接将边界挑战点列为测试点或判定为 RTL bug。禁止 RTL bug 修复后全盘重生成 testplan（应精准重置影响范围）。

### Step 3: 输出验证计划

按模板格式输出，每个测试点包含：

| 字段 | 说明 |
|:--|:--|
| ID | `{分类}_{序号}`（如 REG_001, SMP_008） |
| 测试点 | 简短描述 |
| 场景 | 具体操作步骤 |
| 预期结果 | 可量化的检查条件 |
| 优先级 | P0/P1/P2 |
| Spec 引用 | spec 章节号 |
| RTL 位置 | 对应文件+行号 |
| 状态 | 空（待验证）/ ✅（已通过） |

输出模板示例：

```markdown
| ID | 测试点 | 场景 | 预期结果 | 优先级 | Spec | RTL |
|:--|:--|:--|:--|:--:|:--|:--|
| REG_001 | 复位默认值 | 复位后读所有寄存器 | 每个寄存器值为 spec 定义值 | P0 | 3.1 | regfile.v:282 |
| REG_002a | 32-bit pattern sweep | 全部 RW 寄存器写全1/全0/5A5A5A5A/A5A5A5A5 读回比对 | RW 寄存器读回=写入值(mask 后比对),RO/W1C/WO 跳过 | P0 | 3.1 | regfile.v |
```

### 寄存器验证必做测试点（强制规则）

每个含寄存器接口的模块，testplan 必须包含以下寄存器验证测试点：

| ID | 测试点 | 说明 | 优先级 |
|:--|:--|:--|:--:|
| REG_001 | 复位默认值 | 复位后读所有寄存器，每个寄存器值为 spec 定义值 | P0 |
| REG_002 | 写后读 | 每个 RW 寄存器写随机值后立即读回 | P0 |
| **REG_002a** | **32-bit pattern sweep** | **全部 RW 寄存器写 4 种 pattern 读回比对** | **P0** |
| REG_003 | RO 写保护 | 向 RO 寄存器写值，读回无变化 | P1 |
| REG_004 | WO 自清零 | 写 WO 位后读回为 0 | P0 |
| REG_005 | 保留位读 0 | RSVD 位读回 0 | P1 |
| REG_006 | 地址边界 | 未定义地址访问返回 0 | P1 |

#### REG_002a: 32-bit pattern sweep（强制必做）

> **设计动机**：单纯的"写一个值读回"无法发现位 stuck-at、相邻位短路、
> 读写隔离等常见寄存器缺陷。4 种互补 pattern 能系统性覆盖每一位的
> 0→1 和 1→0 翻转，是寄存器验证的基础测试。

**4 种 pattern**：

| Pattern | 值 | 检测目标 |
|:--|:--|:--|
| 全1 | 0xFFFFFFFF | 位 stuck-at-0 |
| 全0 | 0x00000000 | 位 stuck-at-1 |
| 5A5A5A5A | 0x5A5A5A5A | 位翻转、相邻位短路 |
| A5A5A5A5 | 0xA5A5A5A5 | 反向位翻转 |

**比对规则**：
- **RW 寄存器**：读回必须 == 写入值（mask 后比对），**必须比对**
- **RO/W1C/WO 寄存器**：跳过不比对
- **mask 处理**：RSVD 位、自清零位、WO 位、RO 位需用 mask 排除

**实现要点**：
- 每个寄存器用 mask 过滤可写位：`wr_val = pattern & mask`
- 读回后也 mask：`(rd & mask) == wr_val`
- 每个寄存器前 SW_RST 清干净，确保起始状态干净
- 汇总每个寄存器 4/4 patterns passed

**覆盖率价值**：pattern sweep 让所有 RW 寄存器位都翻转，
显著提升 toggle 覆盖率（实测 regfile toggle 69.53%→84.50%，seq_fsm 79.21%→94.24%）。

## 验证结果回填

验证计划不是一次性文档。当验证执行有进展时，必须将结果回填到测试点状态列：

| 状态标记 | 含义 | 触发条件 |
|:--:|:--|:--|
| 空 | 尚未验证 | 初始状态 |
| ✅ | 已通过 | 对应测试用例 PASS，确认覆盖到该 RTL 位置 |
| ❌ | 已失败 | 对应测试用例 FAIL，分析后确认不是环境问题 |
| ⏸️ | 阻塞 | 依赖的 RTL bug 未修复，暂不可测 |

回填时机：
- 每次验证运行后，将通过的测试点标记为 ✅
- 每个 RTL bug 修复后，将其影响范围内的测试点从 ✅ 或 ❌ 重置为空
- 合并 MR/PR 前，testplan 中所有 P0 必须为 ✅ 或 ⏸️（标注阻塞原因）

每次 testplan 更新时，必须在文档末尾自动附加变更记录：

```markdown
变更记录示例（追加在文档末尾）：

| 版本 | 日期 | 变更类型 | 变更内容 | 原因 |
|:--|:--|:--|:--|:--|

| v1.1 | YYYY-MM-DD | 新增 | <TP_ID> <新增测试点描述> | RTL review 补漏 |
```

变更类型包括：`新增`、`修正`（改预期）、`删除`、`重置`（回归）、`升级/降级`（优先级变更）。

## 验证评审门禁

测试计划输出后，必须通过以下评审才能进入 `/testcase-gen`：

| 检查项 | 通过标准 |
|:--|:--|
| 完整性自检 | Step 2 的 6 项检查全部通过 |
| 一致性 | 每个测试点的 spec 引用能对应到 spec 文档的实际内容 |
| RTL 映射 | 每个 P0 测试点的 RTL 位置能对应到实际代码行 |
| 优先级共识 | 所有 P0 测试点经设计团队确认无遗漏 |
| 不可测点处理 | 所有不可测点已标注原因并归档 |
| 覆盖率目标 | 覆盖率目标已定义且可衡量 |


## 覆盖率映射规则

每个测试点必须明确标注它覆盖的 RTL 代码范围：

| 规则 | 要求 |
|:--|:--|
| P0 测试点覆盖映射 | 每个 P0 测试点必须指定其覆盖的 RTL 文件+模块 |
| FSM 覆盖 | 每个 FSM 必须有 ≥1 个测试点覆盖其所有状态和主要转移路径 |
| CDC 覆盖 | 每个 CDC 路径必须有 ≥1 个测试点验证数据完整性 |
| 边界覆盖 | 所有边界挑战测试点必须有覆盖率收集方式（covergroup / assertion） |
| 寄存器覆盖 | 每个寄存器位域必须在测试计划中有对应检查点 |



## 测试计划维护（RTL 变更时）

测试计划不是一次性文档。当 RTL 发生以下变更时必须更新：

| 变更类型 | 更新动作 | 示例 |
|:--|:--|:--|
| **寄存器新增/删除** | 追加/移除对应测试点，更新地址映射 | 新增 DMA_CFG2 寄存器 |
| **寄存器位域变更** | 更新测试点的预期结果 | DATA_ALIGN 从 2-bit 扩展到 4-bit |
| **FSM 状态/转移变更** | 更新/追加 FSM 测试点 | 新增 ST_FAST_SAMPLE 状态 |
| **CDC 路径变更** | 追加 CDC 同步测试点 | 新增 cal_done 同步路径 |
| **接口端口变更** | 更新端口测试点 | apb_if 增加 PSTRB 信号 |
| **时序参数变更** | 更新边界测试条件 | SPT 最大值从 240 变为 128 |

**触发时机**：每次 RTL commit 后，diff 中涉及上述变更类型时，自动触发 testplan 增量更新。
**版本管理**：测试计划文档纳入 git 管理，版本号与 RTL 版本对齐。

## vs Spec Gap 分析（生成/更新后必须执行）

> **痛点来源**（示例：某项目曾发生）：testplan 生成后标 63 个测试点全 ✅，但
> 未核对 spec 功能点是否全覆盖——N 个 spec 功能点（关键握手时序约束、抢占时机、
> 独立使能位、触发源等）无对应测试点。
> testplan 自身完整 ≠ 覆盖 spec。本子流程查 spec→testplan 这一层 gap。

生成或更新 testplan 后，逐项核对 spec 功能点覆盖：

### Step G1: 提取 spec 功能点

从 spec 逐章提取可验证功能点：
- §1 特性列表 → 每条特性
- §2 接口定义 → 每个时序约束（如"<握手信号 X> 先于 <握手信号 Y> 至少 1 周期"）
- §4 功能描述 → 每个子流程/异常路径/组合场景
- §3 寄存器 → 每个独立使能位/属性（RW/RO/W1C/WO/RSVD）

### Step G2: 逐功能点查测试点

| spec 功能点 | spec 位置 | testplan 有测试点? | 测试点 ID | gap? |
|:--|:--|:--:|:--|:--:|
| <功能点> | §x.y | 是/否 | <ID> 或 — | G1 |

### Step G3: G1 缺口处理

- **spec 有功能点但 testplan 无测试点**：
  - 可测 → 补测试点（追加到 §3 测试点清单）
  - 不可测（芯片级时序/物理）→ 标"验证范围外"并说明原因
  - RTL 无此逻辑 → 标"spec 待实现"（可能 spec 超前于 RTL，需决策）

### Step G4: 输出 gap 清单

```
spec→testplan gap 清单（示例）：
G1.1 <握手信号 X> 先于 <握手信号 Y> 1 周期时序约束（§x.x）— 无测试点 — 可测，建议补 SVA + 定向 case
G1.2 <某场景> 时机抢占（§x.x FSM 转移表）— 仅 <TP_ID> 间接 — 建议补独立 <TP_ID_new>
G1.3 <N 个独立使能位>（§x.x）— 无测试点 — 补 N 个测试点
...
```

> **与 verify-completeness 分工**：本子流程只查 spec→testplan 一层（testplan
> 生成时的自检）。verify-completeness 查全链路三层（spec→testplan→sequence），
> 是独立审计。本子流程是第一道防线，verify-completeness 是第二道。
> 详见 `/verify-completeness` 和 `/verify-flow`。

## 覆盖率收尾门禁

停止补充测试用例并进入下一阶段的条件：

| 门禁条件 | 要求 |
|:--|:--|
| 语句覆盖率 | 100%（对所有 RTL 模块） |
| 分支覆盖率 | 100% |
| 条件覆盖率 | ≥90% |
| FSM 覆盖率 | 所有状态至少到达一次，所有转移触发一次 |
| 功能覆盖率 | 所有 P0 测试点通过，P1 ≥ 90% 通过，P2 不做硬性要求 |
| 不可测点 | 所有标记为"不可测"的点已归档并经设计确认 |
| 回归测试 | 全部通过的回归测试套件已入库（`make check` 无失败） |

**未达标时，必须补充对应的测试用例，不降低门禁标准。**

## 通用测试点分类模板

适用于大多数 RTL 模块的测试点分类，按模块类型选择使用。**注意：此模板仅作为参考起点，不可替代 Step 1 的并行分析。**

### 数模混合控制器模块（示例：ADC 控制器）

> **以下为 ADC 控制器的测试点模板示例。** 其他数模混合模块（DAC/PWM 等）参照
> 此结构，按自身模拟接口信号替换。本节展示"寄存器配置接口连接性 + 时序接口信号"
> 两类验证的组织方式。

对含有模拟接口的控制器模块（ADC 控制器、DAC 控制器、PWM 等），数模接口必须全部检查。分两类：

#### ① 寄存器配置接口 — 连接性检查

验证从 APB 寄存器到模拟顶层接口的每一条路径：

| 测试点 | 场景 | 优先级 | 说明 |
|:--|:--|:--:|:--|
| 通道选择连通性 | 配置 LP_SEQ/HP_SEQ 各通道号，检查 ch_sel 线上值 | P0 | 覆盖所有通道号（0~31），确认寄存器写入值与输出信号一致 |
| 采样时间配置 | 配置 SPT0/SPT1 各档位，检查 MUXON 高电平宽度 | P0 | 覆盖所有 SPT 档位（3/8/14/29/42/56/78/240 cycles） |
| 触发源配置 | 配置 TRIG 各触发源选择，检查对应触发路径 | P0 | 软件触发、MCTM 各源、组合源 |
| 对齐方式配置 | 配置 DATA_ALIGN，检查 CH_DATA 对齐方式 | P1 | 右对齐/左对齐 |
| 连续模式配置 | 配置 CONT_MODE，检查序列完成后是否自动重启 | P1 | |
| 使能/复位路径 | ADC_EN=0/SW_RST=1 时所有模拟接口状态 | P0 | 全部回到默认值 |

**关键原则**：寄存器→模拟接口的连接性验证不能只靠数据正确性间接证明。即使数据匹配，也不代表 ch_sel 在正确的时刻切换到了正确的通道。必须对每条路径做直接的信号层验证。

#### ② 有时序要求的接口信号 — 时序检查

对每个带时序约束的信号，严格按 spec 定义的驱动沿/采样沿检查：

| 测试点 | 场景 | 优先级 | 说明 |
|:--|:--|:--:|:--|
| SOC 时序 | SOC 脉冲宽度、驱动沿（spec 定义） | P0 | 正常采样和 preempt 场景下分别检查 |
| MUXON 时序 | MUXON 高电平宽度（= SPT cycles）、下降沿时机 | P0 | 正常采样、preempt_abort、连续模式 |
| ch_sel 切换序列 | 通道切换顺序（特别是 preempt 时） | P0 | 独立检查 ch_sel 序列，不依赖数据正确性 |
| EOC 时序 | EOC 脉冲宽度、采样沿 | P0 | 正常和 overflow 场景 |
| 校准接口 | CAL_ST 脉冲、CAL_DONE 采集 | P1 | |
| Preempt 路径序列 | LP→HP→LP 全路径的 ch_sel 切换 | P0 | 验证 preempt_abort 时立即切到 HP_CH，HP 完成后恢复 LP 位置 |

**示例**（ADC 控制器 HP 抢占时的 ch_sel 验证）：
```
配置：LP_SEQ = CH1（单通道）、HP_SEQ = CH8（单通道）
预期 ch_sel 序列（SOC 时刻观察）：
  ① 0（复位默认，首次 SOC 时 muxon_fall 尚未更新）
  ② 8（preempt_abort 强制切换到 HP_CH）
  ③ 8（LP 恢复 SOC，ch_sel 仍保持上一值）
验证方法：scoreboard 维护预期队列，每个 SOC 事件 pop front 对比
不依赖：EOC 数据匹配
检出能力：如果 preempt_abort 未正确切换 ch_sel，序列会停在 0
```

| 测试点 | 场景 | 优先级 |
|--------|------|:------:|
| 寄存器复位值 | 复位后默认值正确 | P0 |
| 寄存器写/读回 | 写值能否正确读回 | P0 |
| 位域独立访问 | 修改一个位域不影响其他位域 | P1 |
| 只读位写保护 | 向 RO 位写值无影响 | P1 |
| 保留位读回 0 | Reserved 位读回 0 | P1 |
| 地址边界 | 有效地址最后一个和第一个之外返回 0 | P1 |
| 背靠背传输 | 连续写后立即读 | P0 |
